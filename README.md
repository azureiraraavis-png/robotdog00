# robotdog00 — Go2 PRO 한국어 안내 로봇

Unitree Go2 PRO가 **한국어로 말하면서 방문객을 안내하도록** 만드는 프로젝트입니다.

앱에 딸린 음성 비서(벤벤)는 한국어를 알아듣지 못하고 손댈 수도 없습니다.
그래서 앱을 거치지 않고 **PC에서 로봇에 직접 붙어**, 한국어 음성을 만들어
로봇 스피커로 내보내고, 한국어 명령으로 움직이게 합니다.

> A Korean-language voice guide built on the Unitree Go2 PRO.
> The stock BenBen assistant is a closed loop to Unitree's servers with no way to add
> Korean, so this controls the robot directly over the same WebRTC path the app uses —
> local Whisper for Korean speech recognition, edge-tts for synthesis, played through
> the robot's own speaker. Documentation is in Korean; the findings section below may
> be useful to anyone working with a Go2, especially on a non-English Windows locale.

## 왜 앱으로는 안 되는가

앱 안의 **벤벤(BenBen)** 음성 대화는 `앱 → 유니트리 서버 → 앱` 으로 닫힌 구조입니다.
공개된 API도 없고, 한국어를 추가할 창구도 없습니다. 벤벤을 고치려는 시도는 계속 막힙니다.

대신 **앱이 쓰는 것과 똑같은 WebRTC 통신 경로**로 로봇에 직접 붙습니다.
펌웨어 개조도, 탈옥도 없습니다. 그러면 이런 것들이 가능해집니다.

| 하고 싶은 것 | 방법 |
|---|---|
| 한국어 알아듣기 | PC/폰에서 처리 (Whisper, 브라우저 음성인식, 안드로이드 STT) |
| 한국어로 대답하기 | TTS로 mp3 생성 → **로봇 스피커로 재생** |
| 걷기·제스처 | sport 명령 직접 전송 |

**로봇 스피커 재생은 Go2 PRO/EDU에서만 지원됩니다.** 우리 기체는 PRO이므로 해당됩니다.

## 준비물

- **Windows PC** (또는 노트북) — **Python 3.10 ~ 3.12** (3.13/3.14는 안 됩니다, 아래 참고)
- **ffmpeg** — 음성 변환에 필요합니다

- **유니트리 계정** — AES 키를 받으려면 이 기체가 바인딩된 계정이어야 합니다

## 네트워크 구성

가장 안정적인 조합입니다.

```
   폰 (핫스팟 제공, 셀룰러로 인터넷)
     ├── 로봇 Go2 PRO      ← 같은 LAN
     └── PC (이 코드 실행)  ← 같은 LAN + 인터넷
```

로봇을 **AP 모드가 아니라 Wi-Fi(STA) 모드**로 붙여야 합니다.
앱에서 `Device → 네트워크 설정 → Wi-Fi 모드` 로 전환하세요.
앱의 로봇 목록에서 `Off-line` 이 `On-line` 으로 바뀌면 성공입니다.

로봇의 IP는 앱의 기기 정보에서 확인할 수 있습니다.

## AES 키 받기

**펌웨어 1.1.15 이상은 기기별 AES-128 키가 없으면 연결이 거부됩니다.**
이 기체는 업데이트를 여러 번 했으므로 해당될 가능성이 높습니다.

**한국어 Windows 에서는 딸려오는 `unitree-fetch-aes-key` 명령이 동작하지 않습니다.**
대신 이 폴더의 스크립트를 쓰세요.

```powershell
.\.venv\Scripts\python.exe get_aes_key.py
```

비밀번호는 프롬프트로 물어봅니다. **명령줄에 적지 마세요** — 특수문자를 PowerShell이
해석해버리고, 히스토리 파일에 평문으로 남습니다.

성공하면 바인딩된 로봇 목록과 함께, 그대로 붙여넣을 수 있는 환경변수 설정 줄을 출력합니다.

> **왜 별도 스크립트인가**
> 라이브러리가 HTTP 헤더에 시스템 시간대 이름을 그대로 넣는데, 한국어 Windows에서는
> 그 값이 `"대한민국 표준시"` 로 나옵니다. HTTP 헤더는 latin-1만 허용하므로
> `UnicodeEncodeError: 'latin-1' codec can't encode characters in position 0-3` 로
> 죽습니다. `get_aes_key.py` 는 그 헤더만 안전한 값으로 바꿔치기해 우회합니다.
> 라이브러리 파일 자체는 건드리지 않습니다.

- **이 기체가 그 계정에 바인딩되어 있어야 합니다.** 공용 장비라면 관리자에게
  계정 접근이나 키 값을 요청하세요.
- 계정이 중국 가입이면 `config.py` 의 `UNITREE_REGION` 을 `"cn"` 으로 바꾸세요.

받은 32자리 키를 환경변수에 넣습니다.

```powershell
$env:GO2_IP = "192.168.x.x"
$env:GO2_AES_KEY = "여기에32자리16진수"
```

매번 입력하기 번거로우면 `config.py` 의 기본값을 직접 고쳐도 됩니다.
단, 그 경우 키가 파일에 남으니 외부 공유에 주의하세요.

## 리모컨 — ISS 동반 리모컨 (Companion Remote)

이 기체에 딸려온 것은 게임패드형이 아니라 **막대 모양의 동반 리모컨**입니다.
조이스틱 하나, 윗면에 `⏻` `P` `M`, 옆면에 `1` `2` 버튼이 있습니다.

**`L2+B` 같은 조합은 없습니다.** 인터넷의 Go2 자료 대부분은 게임패드형 기준이라
그대로 따라 하면 안 됩니다.

| 버튼 | 조작 | 하는 일 |
|---|---|---|
| **`P`** | **짧게 두 번** | **엎드림 → 댐핑 → 일어서기 순환.** 힘을 빼는 가장 빠른 방법 |
| `P` | 길게 1초 | 뒤집혔을 때 일으키기 |
| `M` | 한 번 | 동반 모드를 나와 **조이스틱 조종**으로 전환 |
| `M` | **빠르게 두 번** | ⚠ **자동 추종 시작** (최대 1.5m/s) |
| `M` | 추종 중 다시 두 번 | ⚠⚠ **고속 추종** (최대 3.0m/s) |
| 옆면 `2` | 두 번 / 한 번 | 장애물 회피 켜기 / 끄기 |
| 옆면 `1` | 한 번 / 두 번 | 반시계 / 시계 방향 약 5.7도 회전 |
| `⏻` | 짧게 / 길게 2초 | 리모컨 켜기 / 끄기 |
| 조이스틱 | — | 조종 모드에서 이동 |

### ⚠ 전용 비상 정지 버튼이 없습니다

**`P` 를 짧게 두 번** 누르는 것이 가장 가까운 대체입니다. 다만 순환식이라
**한 번에 댐핑으로 가지 않을 수 있습니다.** 시연 전에 반드시 손에 익혀두세요.

추종을 멈추려면 `M` 한 번 또는 조이스틱을 건드리면 됩니다.

### ⚠ `M` 두 번은 위험합니다

3.0m/s는 사람이 뛰는 속도입니다. 실수로 두 번 누르면 **로봇이 리모컨을 든 사람을
향해 달려옵니다.** 방문객 앞에서는 절대 일어나선 안 되는 일이므로,
운영자에게 이 버튼을 분명히 알려두세요.

> 이 표는 제조사 매뉴얼을 근거로 정리했지만, **실기로 하나씩 확인하는 것을 권합니다.**
> 특히 `P` 두 번이 실제로 힘을 빼는지는 걷게 하기 전에 눈으로 보셔야 합니다.

### 그리고 이 리모컨이 '사람 따라다니기'의 답입니다

`M` 두 번이 바로 **ISS 2.0 자동 추종**입니다. 카메라로 사람을 알아보는 게 아니라
**리모컨의 위치를 무선으로 쫓는** 방식이라, 가림이나 조명에 강합니다.
안내 담당자가 리모컨을 들고 앞서 걸으면 로봇이 따라옵니다.

영상 인식으로 특정 인물을 추적하는 것보다 훨씬 안정적이니,
추종 기능이 필요해지면 이쪽을 먼저 검토하세요.

## ⚠ 전원을 켤 때 발버둥치는 문제

로봇이 켜자마자 뒤집히거나 네 발을 빠르게 휘젓는 일이 있습니다.
원인은 두 가지가 겹친 것입니다.

1. **시작 자세가 잘못됨** — 다리가 벌어진 채로 켜면 기립 동작이 몸을 밀어냅니다
2. **자동 복구(Auto Recovery)** — 로봇이 "넘어졌다"고 판단해 스스로 일어나려 합니다.
   바닥이 미끄럽거나 자세가 이상하면 성공하지 못하고 **계속 재시도**하는데,
   그게 발버둥치는 것처럼 보입니다

### 소프트웨어로 막을 수 없는 구간

**전원을 켜는 그 순간은 코드로 손댈 수 없습니다.** 우리 프로그램이 로봇에
붙기 전이기 때문입니다. 이 구간은 절차로만 막습니다.

- [ ] **배가 바닥에 닿고 다리를 완전히 접은 상태**로 눕혀 놓고 켜기
- [ ] 평평하고 미끄럽지 않은 바닥 (매끈한 타일 위에서는 특히 잘 미끄러집니다)
- [ ] **켜는 사람이 리모컨을 손에 들고 있기** — `P` 버튼 두 번이 가장 빠른 정지
- [ ] 발끝 비닐 제거 (접지가 없으면 기립에 실패하고 넘어집니다)

### 헷갈리기 쉬운 두 가지 — 자동 복구 ≠ 힘 빼기

별개의 장치입니다. 둘 다 필요합니다.

| | 무엇을 막나 | 어떻게 |
|---|---|---|
| **자동 복구 끄기** | 넘어졌다고 판단해 스스로 일어나려는 **발버둥** | 연결할 때 자동 |
| **댐핑(Damp)** | 관절에 힘이 들어가 자세를 **버티는 것** | 명시적으로 실행 |

`01_connect_test.py` 는 자동 복구만 끕니다. 로봇을 움직이지 않는 스크립트라
힘은 빼지 않아요. 그래서 실행 후에도 로봇은 **서서 균형을 잡고 있고**,
들어 올리면 다리가 자세를 유지하려 저항합니다. 그건 발버둥이 아니라 버티기입니다.

출력의 `몸높이` 로 구분할 수 있습니다. **0.3 안팎이면 서 있는 것**이고,
**0.1 아래면 엎드려 힘이 빠진 것**입니다.

### ⚠ 들어 올릴 때가 특히 위험합니다

전원이 켜진 로봇의 **등 손잡이를 잡고 들어 올리면 발이 땅에서 떨어집니다.**
로봇은 그것을 **넘어진 것**으로 해석하고 스스로 일어나려 발버둥칩니다.
다리가 빠르게 꺾이며 움직이므로 **손이 그 사이에 있으면 다칩니다.**

옮기기 전에 반드시:

```powershell
.\run carry.py
```

자동 복구를 끄고 힘을 뺀 뒤, **연결을 열어둔 채 대기**합니다. 옮기는 동안
설정이 유지되도록 그 창은 닫지 마세요. 다 옮기면 Enter.

리모컨의 `P` 버튼을 두 번 눌러 힘을 뺀 뒤 들어 올려도 됩니다.

### ⚠ 자동 복구 설정은 재부팅하면 초기화됩니다

실측으로 확인했습니다. 껐더라도 **전원을 껐다 켜면 다시 켜져 있습니다.**

그래서 이 프로젝트는 **연결할 때마다** 자동으로 끕니다 (`common.connect()` 안에서).
어떤 스크립트를 실행하든 붙는 순간 꺼지므로, 따로 신경 쓰지 않아도 됩니다.

다만 **전원을 켜고 아직 아무것도 연결하지 않은 구간**은 여전히 무방비입니다.
그 사이에 들어 올리거나 자세를 흐트러뜨리면 발버둥칩니다.
켠 직후에는 아무것이든 한 번 연결해서 설정을 꺼두는 것이 안전합니다.

```powershell
.\run 01_connect_test.py     # 30초, 로봇을 움직이지 않으면서 자동 복구를 꺼둡니다
```

### 소프트웨어로 되는 것

연결한 뒤부터는 아래가 일합니다.

```powershell
.\run recover.py          # 힘 빼고 → 자동 복구 끄고 → 필요하면 일으키기
.\run recover.py off      # 자동 복구만 끄기
.\run recover.py on       # 다시 켜기
```

- **자동 복구 끄기** — 넘어져도 발버둥치지 않고 가만히 있습니다.
  사람이 상황을 보고 판단할 수 있게 됩니다. **시연 환경에서는 꺼두는 쪽을 권합니다.**
- **자세 감시(Watchdog)** — `02`, `04`, `05` 는 실행 중 로봇의 기울기를 지켜보다가
  60도를 넘으면 **즉시 힘을 뺍니다**. 쓰러진 채로 관절에 힘이 들어가 있으면
  모터가 계속 버티려 하면서 발열과 마모가 생기기 때문입니다.
  이 스크립트들은 시작할 때 자동 복구도 함께 끕니다.

### 이미 발버둥치고 있다면

1. **리모컨 `P` 버튼 두 번** — 가장 빠릅니다. 손에 있다면 이것부터
2. 리모컨이 없으면 `.\run recover.py` — 붙는 데 2~3초 걸립니다
3. **그동안 손을 대지 마세요.** 다리가 빠르게 움직입니다
4. 완전히 뒤집혔으면 스스로 못 일어납니다. 힘을 뺀 뒤 **손으로 배가 바닥을
   향하도록 돌려 눕히고** 나서 일으키세요

## 앞으로의 방향

이 폴더가 검증하는 것은 **"PC가 로봇을 제어하고 한국어로 말하게 할 수 있다"** 까지입니다.
그다음은 이렇게 이어집니다.

```
방문객 한국어 발화
  → 마이크 (지향성 USB 마이크 권장 — 전시장은 시끄럽습니다)
  → 한국어 STT   (Whisper / 브라우저 Web Speech API / 안드로이드 STT)
  → 의도 분류 또는 LLM
  → ├ 한국어 TTS → 로봇 스피커   ← 이 폴더에서 이미 검증됨
    └ sport 명령 → 로봇 동작      ← 이 폴더에서 이미 검증됨
```

**APK는 마지막에 만드세요.** 순서를 이렇게 잡으면 위험이 훨씬 적습니다.

1. **지금 여기** — PC 파이썬으로 제어와 음성 검증
2. **웹앱** — PC에서 페이지를 띄우고 폰 크롬으로 접속.
   브라우저의 Web Speech API가 한국어 STT/TTS를 공짜로 해줍니다. APK 불필요.
   (마이크 권한 때문에 HTTPS가 필요합니다 — 로컬 터널로 해결)
3. **APK** — 웹앱이 검증된 뒤 WebView로 감싸거나 네이티브로 재작성.
   이 시점엔 무엇을 만들지가 이미 확정되어 있습니다.

전시장 네트워크가 못 미더우면 안드로이드 **오프라인 한국어 인식**을 내려받아 두면
고정 어휘로는 인터넷 없이도 동작합니다.

## 삽질 기록 — 이 프로젝트에서 알아낸 것들

문서 어디에도 없어서 직접 부딪혀 알아낸 것들입니다.
같은 자리에서 헤매지 않도록 남겨둡니다.

### 오디오

**1. mp3 가 끝나면 송신 루프가 죽습니다**
`MediaPlayer` 로 만든 트랙을 `pc.addTrack()` 하면 첫 파일은 잘 나갑니다. 그런데 파일이
끝나는 순간 트랙이 `MediaStreamError` 를 던지고, 그걸 받은 aiortc 송신 루프가 **종료**됩니다.
그 뒤로는 `replaceTrack()` 으로 새 음원을 꽂아도 읽어가는 쪽이 없어 영원히 무음입니다.
→ **끝나지 않는 트랙**을 만들어야 합니다. 재생할 게 없으면 무음 프레임을 계속 내보내
   송신 루프를 살려두고, 내부에서 음원만 갈아끼웁니다. (`common.ContinuousAudioTrack`)

**2. 무음 프레임의 박자를 `sleep(0.02)` 로 세면 안 됩니다**
매번 20ms 보다 조금씩 더 걸려서 **실측 1.8% 씩 뒤처집니다** (1분에 약 1초).
그만큼 수신 버퍼가 말라가다 소리가 끊기고 결국 멈춥니다.
→ 시작 시각 기준으로 각 프레임이 나가야 할 시각을 계산해 기다립니다. (실측 0.1%)

**3. 오디오 채널을 명시적으로 켜야 합니다**
`switchAudioChannel(True)` 를 보내지 않으면 트랙을 보내도 스피커에서 소리가 안 납니다.
라이브러리 예제(`play_mp3.py`)조차 이 호출을 빠뜨리고 있습니다.

**4. `replaceTrack` 은 동기 함수입니다**
`await` 를 붙이면 `TypeError` 가 납니다. (aiortc 1.15 기준)

**5. 스피커 볼륨 눈금이 비선형입니다**
1~2 는 거의 안 들리고 7 이상은 꽤 큽니다. 실용 구간이 3~6 으로 좁습니다.
미세 조정은 TTS 쪽 음량(`edge-tts` 의 volume)으로 하는 편이 낫습니다.

### 연결

**6. 연결을 닫지 않고 종료하면 유령 세션이 남습니다**
로봇은 한 번에 하나의 WebRTC 클라이언트만 받습니다. `Ctrl+C` 로 그냥 빠져나오면
로봇 쪽에 세션이 남아 다음 실행이 이상하게 동작합니다. `finally` 로 반드시 닫으세요.

**7. `input()` 이 연결을 끊습니다**
asyncio 루프 안에서 그냥 `input()` 을 부르면 이벤트 루프가 통째로 멈춥니다.
그동안 심장박동 신호가 나가지 못해 **로봇이 연결을 끊습니다.**
사람이 화면을 읽고 답하는 십여 초면 충분히 끊깁니다.
→ `await asyncio.to_thread(input, ...)`

**8. 명령에 시간 제한이 없으면 조용히 멈춥니다**
연결이 끊긴 뒤 명령을 보내면 오지 않을 응답을 영원히 기다립니다. 화면에 아무 설명도
없이요. `asyncio.wait_for` 로 감싸고, 시간이 지나면 무슨 일인지 알려주세요.

**9. 멀티캐스트가 막혀도 포트 스캔으로 찾을 수 있습니다**
`discover_ip_sn()` 이 실패해도 로봇은 살아 있을 수 있습니다.
같은 대역을 훑어 신호 포트(9991, 8081)가 열린 기기를 찾으면 됩니다. (`find_robot.py`)

### 안전

**10. 자동 복구는 재부팅하면 다시 켜집니다**
`SetAutoRecovery`(MCF 2054) 로 끌 수 있지만 **전원을 껐다 켜면 초기화됩니다.**
→ 특정 스크립트가 아니라 **연결할 때마다** 꺼야 합니다.

**11. 들어 올리면 로봇은 "넘어졌다"고 판단합니다**
등 손잡이를 잡고 들면 발이 땅에서 떨어지고, 로봇은 일어나려 발버둥칩니다.
다리가 빠르게 꺾이므로 손이 그 사이에 있으면 다칩니다.
→ 들기 전에 반드시 자동 복구를 끄고 힘을 빼세요. (`carry.py`)

**12. `Damp` 전에 반드시 `StandDown` 을 거쳐야 합니다**
서 있는 상태에서 곧바로 힘을 빼면 그대로 무너지며 '쿵' 떨어집니다.
제어된 동작으로 눕힌 다음에 힘을 빼세요. (`common.settle()`)

**12-1. `Move` 명령으로는 걷지 않습니다 — 조이스틱 통로를 써야 합니다**
sport 의 `Move`(1008) 를 아무리 보내도 MCF 모드에서는 **걸음을 떼지 않고 몸통만
기울입니다.** 자세 조정으로 해석되는 것으로 보입니다. 오류도 안 나고 명령은
정상적으로 받아들여지므로, 원인을 짐작하기 어렵습니다.

앱의 조종 화면이 쓰는 **조이스틱 신호 통로**로 보내야 실제로 걷습니다.

```python
pub_sub.publish_without_callback(
    RTC_TOPIC["WIRELESS_CONTROLLER"],
    {"lx": 0.0, "ly": 0.3, "rx": 0.0, "ry": 0.0, "keys": 0},
)
```

- `ly` 전진/후진, `lx` 좌우 게걸음, `rx` 회전
- 값은 **스틱을 기울인 정도 (-1.0 ~ 1.0)** 입니다. m/s 가 아닙니다 (실측은 13-12)
- **50Hz 로 계속 보내야** 합니다. 띄엄띄엄 보내면 멈칫거립니다
- ★ **최소 0.5초 이상 끊김 없이** 줘야 걸음을 뗍니다. 짧게 주면 몸통만
  기웁니다 — 이걸 로봇 문제로 착각해 며칠을 썼습니다 (13-11)
- 끝나면 0 을 여러 번 보내 확실히 세우세요

> ⚠ 아래 "걸음새 명령은 필요 없었습니다"는 맞지만, "`Move` 는 몸통만 기울인다"는
> 결론은 **재확인이 필요합니다.** 13-11 을 먼저 읽으세요.

걸음새 명령(`ClassicWalk`, `ContinuousGait` 등)은 **필요 없었습니다.**
두 통로를 나란히 시험해 확인했습니다. (`gait_test.py`)

**12-2. 몸높이 판정 기준을 너무 낮게 잡으면 안 됩니다**
실측값: 완전히 선 상태 **0.31m**, 엎드림 **0.08m**.
기준을 0.15 로 뒀더니 **아직 일어서는 중인 0.153 에서 통과**해버려,
다음 명령이 기립 도중에 나가 무시되었습니다. 0.24 로 올렸습니다.

**13-1. 자세끼리 직접 오갈 수 없습니다**
`Sit`(앉기)과 `StandDown`(엎드림)은 특수 자세이고, 그 상태에서는 다른 동작 명령이
**조용히 무시됩니다.** 빠져나오려면 전용 명령이 필요합니다.

```
      앉기 ──RiseSit(1010)──┐
                            ├── 서 있기 ──── 다른 모든 동작
    엎드림 ──StandUp(1004)──┘
```

그래서 "앉아" 다음에 "엎드려" 를 하려면 반드시 서 있기를 경유해야 합니다.
바로 보내면 아무 일도 일어나지 않고, 오류도 나지 않아 원인을 찾기 어렵습니다.
→ 현재 자세를 추적해 필요한 탈출 명령을 먼저 보냅니다. (`05_voice_control.py` 의 `Robot`)

**13-3. "서 있다"와 "걸을 수 있다"는 다릅니다 — 조종이 통째로 먹통이 되는 원인**
`StandUp`(1004) 은 관절을 세워 놓기만 합니다. 걷기는 `BalanceStand`(1002) 를 받은
뒤에야 됩니다. 그런데 `BalanceStand` 가 **아직 일어서는 중에 도착하면 조용히
버려집니다.** 그러면 로봇은 멀쩡히 서 있는데 조이스틱 신호를 통째로 무시합니다.

보내는 쪽에는 아무 오류도 없습니다. 화면에는 `W 전진=+0.6` 이 정상적으로 찍히고,
로봇만 가만히 있습니다. 12-2 에서 기준을 0.24 로 올렸지만, 기준을 넘는 순간
바로 다음 명령을 보내는 한 같은 일이 또 일어납니다.

→ 세 가지를 같이 해야 합니다.
1. 몸높이가 **더 이상 오르지 않을 때까지** 기다린 뒤에 `BalanceStand` 를 보낸다
2. 보내고 끝내지 말고, 로봇이 보고하는 `mode` 가 바뀌었는지 **확인하고 다시 보낸다**
3. 힘을 뺀 뒤에는 `StandUp` 이 아니라 `RecoveryStand`(1006) 로 일으킨다
   (`StandUp` 으로 일으키면 서기는 하는데 이동이 먹지 않습니다)

`common.ensure_locomotion()` 이 이 셋을 담당합니다.

**13-4. 상태 메시지에 정답이 들어 있었습니다 — `mode` 와 `velocity`**
`LF_SPORT_MOD_STATE` 는 몸높이만 주는 게 아닙니다.

| 항목 | 뜻 |
|---|---|
| `mode` | 로봇이 **스스로 보고하는 동작 상태**. 걸을 수 있는 상태인지 여기서 알 수 있습니다 |
| `velocity` | `[vx, vy, vz]` **실제 측정 속도**. 명령이 먹었는지 숫자로 확인됩니다 |
| `yaw_speed` | 실제 회전 속도 |

이게 중요한 이유: 지금까지 "움직였는가"를 **눈으로** 판정해 왔습니다. 그래서
'몸통만 기울인 것'과 '진짜 걸은 것'을 구별하는 데 며칠이 걸렸습니다.
`velocity` 를 읽으면 로그만 보고 판정할 수 있습니다.

`mode` 번호의 의미는 펌웨어마다 다를 수 있으므로, 이 기체에서 실제로 어떤 숫자가
나오는지는 `mode_test.py` 로 직접 확인합니다.

**13-5. 조이스틱 입력이 꺼져 있을 수 있습니다**
`SwitchJoystick`(1027) 로 켜고 끕니다. 꺼져 있으면 `WIRELESS_CONTROLLER` 로 보낸
신호가 **통째로 무시되는데, 보내는 쪽에는 아무 오류도 나지 않습니다.**
→ 조종 전에 무조건 한 번 켭니다. (`common.enable_joystick()`)

**13-6. 안전장치가 조작을 삼켰습니다 — 키 두 종류를 섞지 마세요**
`drive.py` 의 데드맨 스위치는 "키를 뗀 지 0.4초가 지나면 없던 것으로" 봅니다.
이동 키에는 맞는 규칙이지만, **자세 키에 같이 적용하면 안 됩니다.**
앉기처럼 3초 걸리는 동작이 끝나고 돌아왔을 때, 그 사이에 누른 키는 이미
0.4초 규칙에 걸려 **버려져 있습니다.** "2 다음에 3을 눌러도 반응이 없다"의 원인이
이것이었습니다.
→ 이동 키는 '지금 눌려 있는가', 자세 키는 '눌렸는가'. 큐를 따로 씁니다.

**13-7. 상태 판단이 틀렸을 때 조작을 막아버리면 안 됩니다**
자세를 문자열로 기억해 두고 `state == "stand"` 가 아니면 조이스틱을 아예 안 보내도록
막았더니, 기록이 어긋난 순간 **멀쩡한 로봇의 조종이 통째로 죽었습니다.**
→ 안내는 하되 신호는 보냅니다. 그리고 기억해 둔 이름표보다 로봇이 보고하는
`mode` 를 우선합니다. 판단 근거가 없을 때(`mode` 를 못 읽을 때)는 막지 않습니다.

**13-8. 이 기체는 `mode` 를 갱신하지 않습니다 — 죽은 계기판을 믿지 마세요**
13-4 를 믿고 `mode` 로 판단하도록 만들었더니, 02 호기는 **서 있든 앉아 있든
엎드려 있든 항상 `mode=0`, `gait_type=0`** 을 보고했습니다. 같은 메시지의

그 결과 멀쩡히 서 있는 로봇을 계속 '이동 불가'로 몰아세웠습니다.

교훈: 새 계기를 붙였으면 **그 계기가 살아 있는지부터 확인해야 합니다.**
안 그러면 죽은 바늘을 보고 멀쩡한 기계를 고장으로 판정하게 됩니다.

**13-9. 명령이 거부돼도 예외가 나지 않습니다 — 응답 코드를 버리고 있었습니다**

**13-10. ~~걷기 모드가 따로 있다~~ — 가설이 틀렸습니다**
"`BalanceStand` 는 자세 잡기 모드라서 몸통만 기운다"는 가설을 세우고,

**13-11. ★ 진짜 원인 — 안전장치가 걸음을 굶겼습니다 ★**

```
0.0초  첫 입력      → 스틱 0.6

0.5초  반복 시작    → 스틱 0.6
```

**무게중심만 옮기고 맙니다.** 이게 며칠 동안 쫓아다닌 '몸통만 기우뚱'의 정체입니다.

→ 데드맨을 두 단계로 나눕니다.

안전성은 오히려 좋아집니다. 잡고 있는 동안은 확실히 이어지고, 놓으면 더 빨리 섭니다.

교훈: **증상을 로봇 탓으로 돌리기 전에 내가 만든 신호의 파형을 먼저 보라.**

**13-11-7. ★ 해결 — 열쇠는 `StopMove` 하나였습니다 ★**
후보마다 새로 고장낸 뒤 변수를 하나씩만 바꿔 쟀습니다.

| 무엇을 했나 | 전진 속도 | 뜻 |
|---|---|---|
| 6초 그냥 기다리기 | 0.026 m/s | 시간 문제가 아님 |
| `BalanceStand` ×3 | 0.022 m/s | **이 명령의 문제가 아님** |
| **`StopMove` 한 번** | **0.498 m/s** | ★ 이것 하나로 풀림 ★ |
| `StopMove` → `BalanceStand` ×3 | 0.550 m/s | |

특수 자세(`Sit`/`StandDown`)에서 빠져나온 직후의 로봇은 아직 '동작 수행 중'으로
남아 있고, 그 상태에서는 조이스틱 입력이 무시되는 것으로 보입니다.
`StopMove` 가 그 동작을 끝내 줍니다.

→ `ensure_locomotion()` 이 **`StopMove` 를 먼저** 보냅니다. 순서가 중요합니다.
  일어서기 절차는 이제 `[탈출명령] → StandUp → StopMove → BalanceStand` 입니다.

이 결과가 앞의 두 결론도 정리해 줍니다.
- 13-11-3 의 "`BalanceStand` 세 번" 은 틀렸습니다. 실제로 효과를 낸 것은
  그 앞에 묻어 있던 `StopMove` 였습니다(13-11-6).
- 13-11-2 의 "`StandUp` 이 차이였다" 도 같은 이유로 의심스럽습니다.
  그때 통했던 `stand_and_wait` 경로에는 다른 요소도 섞여 있었습니다.
  `StandUp` 자체는 해롭지 않으므로 남겨두지만, **확인된 원인은 `StopMove`** 입니다.

**13-11-9. 자동 반복은 큐 안에서 지워지지 않습니다**
도움말이 스무 번 넘게 찍혔습니다. H 를 잠깐 누르고 있으면 윈도우 자동 반복이
초당 30번쯤 들어오는데, 중복 제거를 **큐 안에서만** 하고 있었기 때문입니다.

```
스레드: 큐에 'h' 추가  →  본체: 'h' 꺼냄 (큐 빔)  →  스레드: 'h' 또 추가 …
```

큐가 비는 순간 다음 반복이 '새 입력'이 됩니다. 큐 상태로는 못 거릅니다.
→ **시각으로** 거릅니다. 같은 키가 0.6초 안에 또 오면 누르고 있는 것으로 봅니다.
  (앉기 명령이 스무 번 쌓이는 것도 같이 막힙니다)

곁들여, 조종 시작 전에 콘솔 입력 버퍼를 비웁니다. 연결과 일어서기에 15초쯤
걸리는데 그 사이 누른 키가 쌓여 있다가 한꺼번에 실행되면 위험합니다.

**13-11-8. 끊고 2초 만에 다시 붙으면 실패합니다**
재접속 후보가 `DataChannelTimeoutError` 로 죽었습니다. 로봇 쪽에 이전 세션이
아직 남아 있어서입니다. → `common.reconnect()` 는 12초 기다렸다 붙고,
실패하면 간격을 늘려 세 번까지 다시 시도합니다.

**13-11-5. 자세를 바꾸면 못 걷고, 재접속하면 낫습니다 (원인은 13-11-7)**
앉기든 엎드리기든, 자세를 바꿨다가 일어난 뒤에는 걸음이 나오지 않습니다.
회전조차 실제로 도는 게 아니라 몸을 크게 기울이는 수준입니다.
`RiseSit`·`StandUp`·`BalanceStand`(여러 번)·`RecoveryStand` 어느 것으로도
돌아오지 않았습니다.

**그런데 프로그램을 껐다 켜면 낫습니다.** 로봇을 재부팅하는 게 아니라
연결만 다시 맺는 것인데도요.

이 사실이 중요한 이유: 고장난 것이 **로봇의 자세 상태가 아니라
연결(세션)에 매인 무언가**라는 뜻입니다. 그동안 자세 명령만 뒤지고 있었는데
방향이 틀렸던 것입니다.

→ 당장의 대처: `drive.py` 에서 **`R` 키 = 연결 다시 맺기**. 프로그램을
  껐다 켜지 않아도 됩니다.

**13-11-6. 실험이 스스로를 오염시키고 있었습니다**
`BalanceStand` 세 번이 **실험에서는 통하는데 코드에 넣으면 안 통했습니다.**
같은 명령, 같은 횟수, 같은 간격인데요.

원인은 로봇이 아니라 실험 설계에 있었습니다. `sit_test.py` 는 후보를 적용하기
직전에 '고장 확인' 측정을 하는데, 그 측정이 끝나면서
**조이스틱 신호와 `StopMove` 를 흘려보냅니다.**

```
… → 고장 확인 측정 → [조이스틱 3초] → [StopMove] → 후보 적용 → 측정
                      ↑ 이 둘이 후보에 묻어 있었습니다
```

그러니 "BalanceStand 세 번이 통했다"가 아니라 "조이스틱 + StopMove +
BalanceStand 세 번이 통했다" 였던 겁니다. 그중 무엇이 효과를 냈는지는
가려낼 수 없는 구조였습니다.

일어서기 절차 안의 `BalanceStand` 는 그 앞에 아무것도 없으니 실패했고,
실험 안의 것은 앞에 묻은 게 있으니 성공했습니다. **둘 다 재현성 있는
결과였고, 둘 다 사실이었습니다.** 다른 것을 재고 있었을 뿐입니다.

→ 다시 설계했습니다. 후보마다 **처음부터 다시 고장냅니다.**

```
후보마다:  앉히기 → 일으키기 → 고장 확인 → 후보 적용 → 측정
```

그리고 고장 확인 측정은 `StopMove` 를 보내지 않습니다 — 그것 자체가
회복 요인일 수 있으므로 실험 대상 밖으로 빼둡니다.

가려낼 변수를 하나씩만 바꾼 후보 다섯:

| 후보 | 무엇을 묻는가 |
|---|---|
| 6초 기다리기만 | 시간만 지나면 낫는가 |
| `BalanceStand` ×3 만 | 명령이 필요한가 |
| `StopMove` 한 번만 | 이게 열쇠인가 |
| `StopMove` → `BalanceStand` ×3 | 둘 다 필요한가 |
| 연결 다시 맺기 | 재접속만이 답인가 |

교훈: **효과를 재려면 그 앞을 깨끗하게 만들어야 합니다.** 그리고 첫 후보가
통했다고 멈추면 안 됩니다 — 고친 뒤 **다시 재현해서 확인**까지 해야 끝입니다.
(이 실수를 이 문제 하나에서 두 번 했습니다)

**13-11-4. A/D 가 반대로 돌았습니다 — 회전 부호**
로봇의 `rx` 는 **+ 가 우회전**입니다. 사람이 쓰는 좌표(좌회전 +)와 반대입니다.

```
rx = +0.8  보냈더니  yaw_speed = -1.30 rad/s  (시계 방향 = 우회전)
```

`velocity` / `yaw_speed` 를 읽기 시작하고서야 보였습니다. 그전에는 "로봇이 도네"
하고 넘어갔지 어느 쪽으로 도는지 확인하지 않았습니다.

→ 부호를 뒤집는 곳은 `common.stick_from_intent()` **한 군데뿐**입니다.
  `drive.py`, `move()`, 음성 명령이 각자 뒤집으면 어디선가 반드시 어긋납니다.
  (이 프로젝트에서 같은 지식이 파일마다 흩어져 사고가 난 적이 여러 번입니다)

**13-12. 실측 — 스틱 값과 실제 속도**

| 스틱 | 실제 속도 |
|---|---|
| 0.6 | 약 **1.0 m/s** |

대략 비례한다고 보면 `스틱 ≈ 원하는 속도(m/s) × 0.6` 입니다.
사람 걷는 속도가 1.2 m/s 안팎이니, **0.6 은 실내 안내용으로 꽤 빠릅니다.**
기본값을 0.4(약 0.65 m/s)로 낮췄습니다.

**13-13. `SpeedLevel` 은 거부됩니다 (code = -1)**
MCF 모드에서 `SpeedLevel`(1015) 에 `{"data": 0}` 을 보내면 `-1` 이 돌아옵니다.
지원하지 않거나 파라미터 형식이 다릅니다. 속도는 스틱 값으로 조절하세요.

**13-2. 자동 복구 끄기 ≠ 힘 빼기**
별개입니다. 전자는 발버둥을 막고, 후자는 버티기를 막습니다. 들어 올리려면 둘 다 필요합니다.
`몸높이` 로 구분할 수 있습니다 — 0.3 안팎이면 서 있는 것, 0.1 아래면 힘이 빠진 것.

### 환경

**14. 한국어 Windows 에서 `unitree-fetch-aes-key` 가 죽습니다**
라이브러리가 HTTP 헤더에 시스템 시간대 이름을 그대로 넣는데, 한국어 환경에서는
그 값이 `"대한민국 표준시"` 입니다. HTTP 헤더는 latin-1 만 허용하므로
`UnicodeEncodeError: 'latin-1' codec can't encode characters in position 0-3` 로 죽습니다.
영어 환경에서는 `"Korea Standard Time"` 이라 재현되지 않습니다.
→ 해당 헤더만 바꿔치기해 우회합니다. (`get_aes_key.py`)

**14-2. 윈도우에서는 `pip install` 만으로 CUDA 라이브러리를 못 찾습니다**
`Library cublas64_12.dll is not found` 가 나서 `nvidia-cublas-cu12` 를 깔았는데
**같은 오류가 그대로** 나는 경우입니다.

파이썬 3.8 부터 윈도우에서 확장 모듈이 의존하는 DLL 을 **PATH 에서 찾지
않습니다.** 보안 때문에 바뀐 동작인데, 그 결과 pip 가 아래에 잘 깔아놓아도
아무도 못 찾습니다.

```
.venv\Lib\site-packages\nvidia\cublas\bin\cublas64_12.dll
```

→ `os.add_dll_directory()` 로 그 폴더를 직접 등록해야 하고, 그것도
  **faster_whisper 를 import 하기 전에** 해야 합니다. (`cuda_dlls.py`)

  ※ 등록이 돌려주는 핸들을 붙잡아 두어야 합니다. 지역 변수에만 담으면
    함수를 나가는 순간 등록이 풀립니다.

**14-3. cuDNN 은 버전을 맞춰야 합니다**
`ctranslate2` **4.5.0 부터 cuDNN 9**, 그 아래는 cuDNN 8 입니다.
엇갈리면 `cudnn_ops64_9.dll not found` 가 계속 납니다.
오류 문구의 숫자(`..._9.dll` / `..._8.dll`)가 무엇을 깔아야 하는지 알려줍니다.

실측 (이 PC): `ctranslate2 4.8.2` + `nvidia-cudnn-cu12`(9.x) → **동작**.
RTX 4070 12GB 에서 medium 모델이 CPU 의 small 보다 빠릅니다.

**14-4. 확인은 실제 추론까지 해야 합니다**
`WhisperModel(device="cuda")` 는 CUDA 라이브러리가 없어도 **객체 생성은
성공합니다.** 계산을 시도하는 순간에야 죽습니다. 그래서 "GPU 사용" 이라고
찍어놓고 한참 뒤에 터집니다.
→ `.\run gpu_check.py` 가 6단계(가상환경 → 카드 → 패키지 → DLL → 장치 →
  **실제 추론**)를 순서대로 짚고, 막힌 지점에 맞는 처방을 내놓습니다.

**15. `pyaudio` 는 Python 3.13/3.14 용 휠이 없습니다**
`portaudio.h: No such file` 로 빌드가 실패합니다. Python 3.12 를 쓰세요.

**16. 배치 파일(.cmd)에 한글을 넣으면 안 됩니다**
cmd 는 배치 파일을 바이트 오프셋 기준으로 읽습니다. 멀티바이트 문자로 오프셋이 어긋나면
파일 중간부터 다시 읽는 **무한 루프**에 빠집니다. 순수 ASCII 로 작성하세요.

**17. 펌웨어 1.1.7+ 는 MCF 모드일 수 있습니다**
기본 동작(`StandUp`/`Move`/`Hello`/`Damp` 등)은 `SPORT_CMD` 와 번호가 같지만
곡예·자율 계열은 다릅니다 (`BackFlip` 1044 → 2043, `FreeWalk` 1045 → 2045).
`MOTION_SWITCHER` api_id 1001 로 현재 모드를 먼저 확인하세요.
